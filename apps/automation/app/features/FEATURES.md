This file documents every feature in apps/automation/app/features. Each block below maps to one folder in that directory. A feature without a block here is undocumented and incomplete.

## confluence_sync

- **What it does:** Keeps the local knowledge store in sync with Confluence — ingests webhook events, enqueues idempotent version-guarded jobs, runs them on a crash-safe worker, and reconciles drift the webhook stream missed. Reconciliation scope narrows to the `source_scope` table (PLAN 3.5.6): a `space` root reproduces whole-space sync, a `page` root restricts + tags a page-subtree, and removing/deactivating a root purges what it used to cover.
- **Path / owner:** apps/automation/app/features/confluence_sync — owned by the `automation` application.
- **Language / framework / runtime:** Python 3.12; FastAPI (webhook router), SQLAlchemy 2, APScheduler; runs inside the automation service.
- **Deployment unit:** ships in the single `apps/automation` deployment (infra/automation).
- **Public surface (`__init__.py`, enforced):** `router` (POST /confluence/events), `run_reconciliation`, `drain`, `reap`, `KIND_LIGHTWEIGHT`, `KIND_COMPLETE`, `resolve_scope_roots`, `resolve_space_scope`, `ScopeResolution`, `ROOT_TYPE_SPACE`, `ROOT_TYPE_PAGE`, `resolve_knowledge_scope_tags`, `KnowledgeScopeResult` (PLAN 10.2), `verify_knowledge_scope_coverage`, `KnowledgeScopeCoverage` (PLAN 10.7 — the read-only pre-flip corpus-readiness check; backs `scripts/verify_knowledge_scope_backfill.py`). Everything else (event_service, sync_service handlers, per-job worker internals, reconcile_space) stays internal and is deep-imported only within the feature. Consumers import via `app.features.confluence_sync`; the boundary is checked by `tools/check_feature_boundaries.py` (ADR-0003). (`SlidingWindowRateLimiter` moved to `app.shared.rate_limiter` in PLAN 4.4 — the chat endpoint became its second consumer, and it has no confluence-specific behavior.)
- **Allowed importers:** `app/main.py` (wiring). It imports downward into `ingestion` (shared domain) and `platform`; nothing imports back into it except `main`.
- **Contracts / external systems:** consumes the Confluence event-envelope contract (packages/contracts); calls Confluence Cloud REST v2 for pages/attachments and REST v1 for restrictions + group membership (`HttpConfluenceClient`; v2 restrictions returns 418 — "under construction" per Atlassian's own docs, confirmed live 2026-08-21, not a path typo) and receives Confluence webhooks. `list_space_pages`'s and the group-membership lookup's cursor pagination resolve Confluence's site-root-relative `_links.next` via `httpx.URL.join` (a naive string-concat double-prefixed the `/wiki` context path past the first 100 results — found live 2026-08-21, see `docs/rag/ingestion/phase-4.6.md`). Offline runs/tests use `FixtureConfluenceGateway`. `HttpConfluenceClient.download_attachment` (fixes/phase-2 wiring) fetches an attachment's binary content on any page rebuild, reusing the client's existing auth/timeout/retry/circuit-breaker; capped per-attachment at `confluence_attachment_max_bytes` (default 20 MB, checked both from cheap pre-download metadata and via streaming self-abort so a lied Content-Length can't bypass it) and per-page at `confluence_attachment_max_per_page` (default 200); fails soft (skip + log) per attachment rather than failing the whole sync. Follows Confluence's cross-host redirect to a signed `media.atlassian.com` URL — httpx does not forward the Basic Auth header across that redirect. `sync_service._attachment_blocks` hands the bytes to `ingestion.extract_attachment`.
- **Database tables owned:** `event_ledger`, `job`, `reconciliation_run`, `source_scope`. (It drives, but does not own, the `page_source`/`document`/`document_version`/`chunk`/`page_restriction` tables owned by `ingestion`.) `source_scope` rows are seeded one-off via `scripts/seed_source_scope.py` — no CRUD API yet. `handle_sync_page` (PLAN 4.3) writes `page_restriction` directly — a full delete+insert replace of a page's principal list whenever its access-scope hash changes (or on first index), same convention as the existing direct `page_source`/`chunk` metadata writes in `_apply_metadata_only`.
- **Untrusted input validation:** `server/webhook.py` (HMAC signature, body-size cap, rate limit) and `schemas/events.py::parse_webhook_payload` → Pydantic `EventEnvelope`; unsubscribed event types dropped in `event_service`.
- **Shared components used:** None (backend feature).
- **Tests / risky paths:** `app/features/confluence_sync/tests/` — first-index, atomic re-index (exactly one active version), version-guard drops stale deliveries, permission change = metadata-only (no re-embed) + persists the real principal list to `page_restriction` (full replace, not append; clearing restrictions leaves zero rows), delete/deactivate, job queue (SKIP LOCKED, backoff → dead-letter, lease reaping), rollback, event dedup, webhook security (auth/size/rate/dedup/self-event), and source_scope (pure resolver unit tests + DB-backed subtree-narrowing/tag-propagation/purge-on-removal). `test_knowledge_scope.py` (PLAN 10.2) — pure `resolve_knowledge_scope_tags` unit tests (recognized/unrecognized labels, conflicting provider labels, trim/lowercase); `test_ingestion_pipeline.py` covers the DB-backed wiring: a label-derived tag unions with the page's `source_scope` tags on both `page_source` and every active chunk, and a conflicting label pair contributes no tag and logs `knowledge_scope_conflict`. `test_knowledge_scope_backfill.py` (PLAN 10.7) — real-DB coverage check: all-tagged → ready, untagged/`base`-only → not-ready with the page listed, each recognized scope counts, partial coverage lists only untagged pages, inactive untagged chunks ignored, empty corpus vacuously ready.
- **Run / test:** `make test` or `pytest app/features/confluence_sync/tests`; serve with `uvicorn app.main:app` (set `enable_background_jobs=true` to run the scheduler + in-process worker).

## ingestion

- **What it does:** Turns fetched Confluence content into immutable, atomically-activated indexed versions. Phase 3 builds token-aware parent/child chunks, writes contextual `retrieval_content` (Anthropic contextual retrieval, with a deterministic metadata fallback), embeds children (dense `embedding` + keyword `tsv`), reuses embeddings for unchanged chunks via a 3-pass diff, and routes any embedding-model/dim/schema change through a full re-embed release gate. Change detection/classification, staging → activation → rollback carry over from Phase 2.
- **Path / owner:** apps/automation/app/features/ingestion — owned by the `automation` application.
- **Language / framework / runtime:** Python 3.12; SQLAlchemy 2; runs inside the automation service.
- **Deployment unit:** ships in `apps/automation`.
- **Public surface (`__init__.py`, enforced):** `build_ingestion_services`, `stage_and_activate`, `deactivate_page`, `rollback_to`, `reusable_active_children`, `get_local_state`, `classify`, `decide_body_fetch`, `map_page_status`, `ChangeClass`, `PageHashes`, `TargetVersions`, `extract_attachment`, `ExtractionResult`, `attachment_to_blocks`, and the `normalization` module (re-exported whole — call sites use `norm.Block` / `norm.normalize_body`, ADR-0003 D4). Tokenization, chunking, chunk_diff, and the contextualizer stay internal. Consumers import via `app.features.ingestion`.
- **Allowed importers:** `confluence_sync` (sync/reconciliation) and `retrieval` (reads the chunk index).
- **Contracts / external systems:** OpenAI embeddings and Anthropic messages (contextualization) via `platform.clients.{embeddings_client,anthropic_client}` — both LLM-CALL surfaces (see `security_baseline` below). Attachment parsers (pypdf/python-docx/openpyxl) and `tiktoken` are lazily imported and degrade gracefully when absent; installed via the `attachments`/`tokenizers` optional-dependency groups (`uv sync --extra attachments --extra tokenizers`) for real (non-degraded) extraction.
- **Database tables owned:** `page_source`, `document`, `document_version`, `chunk`, `page_restriction` (ORM in `app/platform/db/models.py`). `chunk.embedding` is `vector(EMBEDDING_DIM)`; its HNSW index casts to `halfvec` for >2000-dim models (pgvector's `vector` HNSW cap is 2000 — see ADR-0002). `page_restriction` (PLAN 4.3) is the persisted per-page principal ACL, FK'd to `page_source.page_id` ON DELETE CASCADE — presence of a row restricts, absence means unrestricted; written directly by `confluence_sync`'s `sync_service.py` (same pattern as `page_source`/`chunk`: this feature owns the table, `confluence_sync` drives writes to it).
- **Untrusted input validation:** None at this layer — inputs arrive already validated at the `confluence_sync` boundary; attachment bytes are parsed defensively (never raise).
- **Shared components used:** None.
- **Tests / risky paths:** `app/features/ingestion/tests/` — token-window invariants, parent/child sizing + stable-key stability, 3-pass diff reuse/re-embed/delete sets, embedding-reuse counts (spy embedder), contextualizer fallback vs LLM path, attachment extraction + OCR gating. DB-level embedding/tsv population, atomic version swap, and the re-embed release gate are covered by `confluence_sync/tests/test_ingestion_pipeline.py`.
- **Attachment content is wired in and searchable (fixes/phase-2 wiring, closes the 4.6.13/4.6.15 PARKED disposition).** `domain/attachment_extraction.py::attachment_to_blocks` wraps each attachment's extracted text as `norm.Block`s under a title-keyed heading path (`["Attachments", title]`) and `confluence_sync/application/sync_service.py::_attachment_blocks` merges them into the page's `blocks` on any rebuild — reusing the exact same section/chunk/diff/embedding-reuse pipeline as page body text; no new table, no new `Chunk` column, no migration. `content_hash`/`structure_hash` deliberately stay body-only (attachment text is never folded in) — see the `_REBUILD_CLASSES` comment in `sync_service.py` for why. **Disclosed limitation:** `ChangeClass.attachment_changed` alone does **not** trigger a rebuild — `DocumentVersion`'s `uq_document_version_idem` constraint is unique per `(document_id, cf_version, retrieval_schema_version, embedding_model)`, and Confluence attachments carry their own version numbers independent of the page's `cf_version`, so rebuilding on attachment-change-alone was tried and hit that constraint's `IntegrityError` live (not a hypothetical). An attachment added/replaced/removed with no other page change is picked up at the *next* rebuild-triggering event (a body edit or a pipeline/config-version bump), not immediately. **Disclosed residual risk:** the size cap (`confluence_attachment_max_bytes`) bounds the *compressed* download only — `pypdf`/`python-docx`/`openpyxl` decompress ZIP-based formats (docx/xlsx) in memory, so a malicious/corrupt attachment could still trigger a decompression-bomb-style memory spike during parsing; accepted for now since attachments originate from an authenticated, single-tenant Confluence instance, not arbitrary internet uploads, and every parser already catches broad exceptions and degrades to empty text rather than crash the sync.
- **Run / test:** `pytest app/features/ingestion/tests` (plus the confluence_sync suite, which drives this feature end-to-end).

## retrieval

- **What it does:** Permission-aware hybrid retrieval over the active chunk index — concurrent dense (pgvector, halfvec-aware) and keyword (tsvector, OR-of-terms ranked by ts_rank) candidate search, fused with Reciprocal Rank Fusion, filtered by an access-scope permission policy, returning relevance-ranked page ids. Status is enforced by the index (only current pages have active chunks); permission is enforced at query time — source-level RLS (Phase 3.5) plus, as of PLAN 4.3, a persisted page-level principal ACL, both layered.
- **Path / owner:** apps/automation/app/features/retrieval — owned by the `automation` application.
- **Language / framework / runtime:** Python 3.12; SQLAlchemy 2 (raw SQL for the vector/tsvector operators); runs inside the automation service.
- **Deployment unit:** ships in `apps/automation`.
- **Public surface (`__init__.py`, enforced):** `HybridRetriever` (the entry point; `retrieve()` for the eval-harness page-id shape, `retrieve_with_context()` for Phase 4.2's chunk id + score + title/url shape, `fetch_parent_texts()` for parent-context expansion), `PrincipalPermissionPolicy` (the pure decision function; its constructor-injected instance now only supplies `space_id()` parsing — PLAN 4.3 builds a fresh, DB-backed instance per search for the `allowed()` check), the `RetrievedHit`/`RetrievalResult` DTOs, and `update_query_trace_answer`/`update_query_trace_feedback` (the Phase 4/4.4 `query_trace` UPDATE writers). Fusion and the low-level search functions stay internal. Consumers import via `app.features.retrieval`.
- **Allowed importers:** the `rag_agent` answer workflow (Phase 4.2) and the evaluation harness. Imports downward into `ingestion` data (the `chunk`/`page_source`/`page_restriction` tables) and `platform`.
- **Contracts / external systems:** the embedding provider (query embedding) via `platform.clients.embeddings_client`.
- **Database tables owned:** none — reads `chunk`/`page_source`/`page_restriction` (owned by `ingestion`; PLAN 4.3's `search_repo.fetch_page_scopes` queries the latter two, scoped to the current candidate page set, never the whole corpus); owns the retrieval-write and answer-update paths on `query_trace` (schema owned by the 3.5.4 migration).
- **Untrusted input validation:** query text is passed to Postgres text-search via bound parameters (Postgres lexemizes it; no string interpolation of user input into SQL).
- **Shared components used:** None.
- **Tests / risky paths:** `app/features/retrieval/tests/` (RRF fusion, permission policy) and `confluence_sync/tests/test_retrieval_eval.py` — the end-to-end eval over the indexed fixture corpus: retrieval_smoke recall@5 held at 1.000 while mrr 0.75→1.00 and ndcg 0.82→1.00 beat baseline, permission proves no cross-scope leak with authorized access preserved, (PLAN 4.2) `retrieve_with_context`/`fetch_parent_texts`/the trace answer+feedback UPDATE writers are exercised against the real indexed corpus, and (PLAN 4.3) `test_permission_enforcement_is_db_backed_not_fixture_fed` proves enforcement holds even with an intentionally empty injected policy — the acceptance proof that the ACL is truly DB-backed, not fixture-fed.
- **Run / test:** `pytest app/features/retrieval/tests app/features/confluence_sync/tests/test_retrieval_eval.py`.

## evaluation

- **What it does:** DB-free RAG evaluation harness — retrieval/latency metrics, a fixture-backed dataset, a runner, a baseline report generator, and (PLAN 3.5.5) rerank-lift reporting: before/after Precision@5 and NDCG@10 comparing a plain-fused ranking against the same ranking with reranking applied, so the reranker's actual contribution is measured, not assumed. **PLAN 9.7 (ADR-0008 decision 7):** two lightweight, non-LLM-judge metrics — `fallback_rate` (fraction of cases that refused or asked for clarification instead of answering) and `citation_grounding_rate` (a faithfulness/hallucination-rate proxy: the fraction of an answer's cited ids within the case's own labelled-relevant set) — plus a new `out_of_corpus` dataset (one case, empty `relevant_chunk_ids`, reusing the closed `answer` `EvalKind`, no new literal) bundled into `run_baseline`.
- **Path / owner:** apps/automation/app/features/evaluation — owned by the `automation` application.
- **Language / framework / runtime:** Python 3.12; pure Python (no DB, no network); runs inside the automation service or standalone.
- **Deployment unit:** ships in `apps/automation` (dev/CI utility; not on the request path).
- **Public surface (`__init__.py`, enforced):** `evaluate`, `evaluate_rerank_lift`, `load_dataset`, `write_rerank_lift_reports`, `load_corpus_loader`, `datasets_dir`, `confluence_fixtures_dir`, `RankFn`, `fallback_rate`, `citation_grounding_rate` (PLAN 9.7), and the `EvalCase` / `EvalDataset` / `EvalResult` / `EvalReport` / `RerankLiftReport` types. `run_baseline` remains a runnable module (`python -m app.features.evaluation.run_baseline`). Consumers import via `app.features.evaluation`.
- **Allowed importers:** standalone tooling; no runtime feature depends on it. `confluence_sync`'s DB-backed test suite imports this feature's root (and, as of PLAN 9.7, `rag_agent`'s) to run real end-to-end fallback assertions — test-only, not a production dependency.
- **Contracts / external systems:** None; reads the Confluence fixture corpus under `tests/fixtures/confluence`.
- **Database tables owned:** None.
- **Untrusted input validation:** None (operates on trusted fixtures).
- **Shared components used:** None.
- **Tests / risky paths:** `app/features/evaluation/tests/` — metrics correctness (PLAN 9.7 adds `test_fallback_metrics.py`: mixed/all/none/empty fallback rates, fully/partially/never-grounded citation rates), fixture loader, baseline runner, and (PLAN 3.5.5) `test_rerank_lift.py` — before/after lift reporting. The DB-backed wiring proof against a real `AnswerService` (PLAN 9.7) lives in `confluence_sync/tests/test_fallback_eval.py` — see `rag_agent`'s own Tests entry.
- **Run / test:** `make eval` or `python -m app.features.evaluation.run_baseline`; `pytest app/features/evaluation/tests`.

## rag_agent

- **What it does:** The grounded answer runtime over the Phase 3.5 retrieval spine (ADR-0005), now wired to a real HTTP surface. A fixed, testable workflow — conversational rewrite → RLS-scoped retrieve → RRF → cross-encoder rerank → **one CRAG corrective retry if weak** → refusal threshold → parent-context expansion → grounded generation with forced numbered citations → citation enforcement → SSE — **not** an agent loop. **Status: Phase 4.2 + 4.3 + 4.4 + 4.5 shipped; Phase 5 caching shipped.** `AnswerService` implements the full pipeline and is unit-tested with fake LLM/retriever collaborators plus DB-integration-tested against the real fixture corpus. `POST /chat` (SSE: `start`/`token`/`citations`/`done`/`error`) and `PATCH /chat/{trace_id}/feedback` are live in `app/main.py`, with the full `securing-http-and-llm-endpoints` control set applied (see `server/router.py`'s `security_baseline` docstring) — PII redaction on every rewrite/generation call, a circuit breaker + abuse cap added to `AnthropicMessagesClient`, and the webhook's `SlidingWindowRateLimiter` promoted to `app.shared.rate_limiter` as its second consumer. **PLAN 5:** `main.create_app` now wraps `AnswerService` in `CachingAnswerService` (`application/answer_cache.py`) — an in-process exact-match TTL cache keyed on `(full history, principal)` that skips retrieval + generation entirely on a byte-for-byte repeat; the pre-existing `Idempotency-Key` replay cache in `server/router.py` was refactored onto the same extracted `app.shared.ttl_cache.TTLCache` primitive. Semantic caching is explicitly not built — see `answer_cache.py`'s docstring for the accuracy-risk rationale. **Small-talk short-circuit (post-4.6):** a greeting or meta question ("hi", "what can you do") is not a retrieval failure and was refusing anyway on any corpus without a lucky keyword match — `domain/small_talk.is_small_talk` (a closed, exact-match classifier, never fuzzy/LLM-based) now routes those straight to `AnthropicAnswerGenerator.generate_small_talk`, an ungrounded reply with no citations and no `query_trace` row, bypassing rewrite/retrieval/CRAG/refusal entirely. A real question that merely starts with a greeting does not match and still runs the full grounded pipeline. Fails open to a static greeting on an `AnthropicError`, unlike `generate`, since an ungrounded reply carries no accuracy risk. **Vision-grounded image analysis (PLAN 7.2-7.6, ADR-0009) — Phase 7 done, 7.7 exit gate closed:** `ChatMessage.images` (only the newest turn is ever analyzed) triggers a second, independent `generate_image_analysis` call — unlike small-talk, retrieval still runs, but `decide_refusal` gains a `has_image` gate so a text-empty-but-image-answerable turn does not incorrectly refuse; the result rides on `Answer.image_analysis`/`ChatDoneEvent.imageAnalysis`, never merged into the grounded, citation-enforced text and never itself passed through `enforce_citations`. The web widget (PLAN 7.5) sends staged attachments on the newest turn and renders both the sent image (click-to-zoom) and a labeled vision-analysis block. A live-model adversarial red-team (PLAN 7.6) against real Anthropic vision calls found zero injection compliance across system-prompt exfiltration, fake-citation, and DAN-style role-switch payloads; C3/C10 image-count/byte caps and the newest-turn-only scope were all confirmed live, not just via unit tests. **PLAN 7.8:** a genuinely text-empty, image-only turn (attach an image, send with no typed text) now skips rewrite/retrieval entirely (`answer()` uses an empty `RetrievalResult()` instead of embedding an empty string — OpenAI's embeddings API rejects that outright with a live 400) and no longer sends Anthropic an empty text content block (`AnthropicMessagesClient._create_message` omits it rather than sending `""`, which Anthropic also rejects live) — both were real, user-reported crashes, not scoped gaps; see PLAN.md 7.8. Disclosed gaps, still open: C6 PII redaction does not scan image bytes (`pii.py`); a small-talk-classified turn with an attached image still short-circuits and drops the image (`answer_service.py`'s module docstring). **Ambiguity/vagueness classifier + clarification bypass (PLAN 9.2/9.3, ADR-0008):** `domain/clarification.py::decide_clarification` (heuristic first — a query long enough to be self-specifying skips the LLM call entirely — then `AnthropicAmbiguityClassifier.classify`, `routing_model` tier, only when inconclusive) is wired into `answer_service.answer` right after the small-talk check (the explicit tie-break ADR-0008 flagged: `is_small_talk`'s whole-message match runs first, so "hi, what's the approval process?" still reaches this branch normally). Feature-flagged `enable_clarification_branch` (default `False`, `settings.py`). When on and the verdict is `is_ambiguous`, PLAN 9.3 bypasses rewrite/retrieval/CRAG/refusal entirely (same shape as small-talk: no `query_trace` row, `refused` stays `False`) and calls `AnthropicAnswerGenerator.generate_clarification` — a second, independent call whose system prompt (`CLARIFICATION_SYSTEM_PROMPT`) asks for a fixed `Question:`/`Options:`/`- ` shape that `domain/clarification.py::parse_clarification_reply` parses deterministically, failing open to a static fallback (never a guessed/partial question) on either an `AnthropicError` or an unparseable reply. The result lands on `Answer.needs_clarification`/`clarification_question`/`clarification_options` and the matching `ChatDoneEvent` fields (`needsClarification`/`clarificationQuestion`/`clarificationOptions`, `packages/contracts`) — additive, no new SSE event, per ADR-0008 decision 3. A non-ambiguous verdict is only logged (`clarification_decision`) and changes nothing. When the flag is off (the default), `decide_clarification` is never called — zero added cost. **Disclosed gap, same reasoning as small-talk's:** an ambiguous query with an attached image gets the clarifying question and the image is silently dropped (`answer_service.py`'s module docstring) — the widget UI to actually render `clarificationOptions` as quick-reply chips is PLAN 9.5, not built yet. **Differentiated refusal copy (PLAN 9.4, ADR-0008 decision 4/5):** `domain/refusal.RefusalReason` is now a closed three-value taxonomy (`no_candidates | weak_score | no_citations`) instead of a free-text diagnostic string — `decide_refusal` returns the category directly, and `answer_service._REFUSAL_COPY` maps each to its own honest, user-facing string (drafted under `copywriting-rules`/`ux-writing`/`anti-ai-writing`) replacing the single identical `_REFUSAL_TEXT` every refusal used to render. `Answer.refusal_reason` is typed to the same closed `Literal`; it still never reaches the `/chat` SSE wire (not on `ChatDoneEvent`), only the internal DTO and the `chat_request` audit log line, which now carries a genuinely static, groupable category (fixing the drift between that log line's own documented contract and its previous interpolated-score reality). Score-level diagnostic detail moved to a dedicated `log.info("refusal", ...)` call so no observability was lost. **Human hand-off stub (PLAN 9.6, ADR-0008 decision 6):** every `refused=True` answer (both refusal branches) now also emits one `human_handoff` structured log record — `trace_id`, `raw_query` (the user's verbatim original text, not the rewritten search string), `refusal_reason`. This is the entire backend hand-off mechanism this phase — no webhook, ticket, or email integration; the widget's matching static "connect me to a human" CTA (`apps/web`) is the frontend half. `raw_query` is a disclosed, deliberate exception to `router.py`'s own "never the raw message" C9_audit rule — it mirrors the pre-existing `query_trace.raw_query` DB column already keyed by the same `trace_id`, so this does not add a new place the text is persisted, only a second place it is read from. Salesforce remains the noted eventual integration target (`docs/future-ideas/IDEAS.md` #1), and the CTA's `test@gmail.com` address is a disclosed placeholder, not a real support channel. **Natural-writing style guidance (user request, 2026-08-13):** `ANSWER_SYSTEM_PROMPT` (`domain/prompt.py`) gained an appended block of plain-language/anti-AI-writing instructions (no filler, no jargon like "leverage"/"pivotal", no invented facts beyond the evidence, no formulaic contrast patterns, no em dashes in the reply) on top of the pre-existing, load-bearing citation-marker instruction — the grounding/citation contract `enforce_citations` depends on is unchanged, only the phrasing style of the generated text changes. Live-verified against the real Anthropic API (not just the mocked-transport unit test): a real answer came back with no em dash, direct wording, and a correctly placed `[1]` marker. Scoped to this one prompt only — `SMALL_TALK_SYSTEM_PROMPT`/`IMAGE_ANALYSIS_SYSTEM_PROMPT` were not extended to match. **Security review (PLAN 9.8) — done, zero findings:** 3 deterministic red-team tests prove the classifier trusts only a leading `AMBIGUOUS` token (never one buried in a hostile completion) and `parse_clarification_reply` structurally discards any text outside the `Question:`/`Options:` shape; a wire-level test locks the `done` event's key set for a clarifying turn so it can never leak `refusalReason`. A live-model adversarial pass (mirroring PLAN 7.6) against the real classifier + clarification calls — system-prompt exfiltration, DAN-style role switch, internal-refusal-category exfiltration, plus a benign control — found zero injection compliance; ### security_baseline (PLAN 4.4 — see `server/router.py` for the full per-control mechanism text)

```yaml
security_baseline:
  applies: true
  surfaces:
    - id: POST /chat
      tier: STATE-MUTATING + LLM-CALL
      controls:
        C1_auth:        { status: covered, mechanism: "shared-secret chat_api_key via Authorization: Bearer, constant-time compare, fail-closed (503) when unset" }
        C2_rate_limit:  { status: covered, mechanism: "SlidingWindowRateLimiter keyed by client IP only (never the caller-reported principal — PLAN 4.6.4 fix), chat_rate_limit_per_minute, bounded to chat_rate_limiter_max_tracked_keys tracked IPs" }
        C3_input:       { status: covered, mechanism: "Pydantic body (extra=forbid); history non-empty + ends on a user turn; chat_max_history_turns / chat_max_message_chars; all-digit principal rejected (PLAN 5.3 red-team finding); PLAN 7.4 (ADR-0009): chat_max_images_per_turn / chat_max_image_bytes checked on every turn's images" }
        C4_timeout:     { status: covered, mechanism: "AnthropicMessagesClient timeout/retry/breaker (answer_timeout_seconds/max_retries/breaker_threshold); retrieval's embedder/reranker already covered (3.5.2/3)" }
        C5_output_rate: { status: covered, mechanism: "generation token cap + chat_output_max_answer_chars defensive re-cap + paced SSE chunks (chat_token_chunk_chars/chat_stream_interval_ms); PLAN 7.3: imageAnalysis gets the same defensive re-cap before it reaches the done event" }
        C6_redaction:   { status: covered, mechanism: "redact_pii scrubs the assembled prompt before every rewrite/generation call; PLAN 7.3 (ADR-0009 decision 6): does NOT extend to image bytes on ChatMessage.images — disclosed, accepted gap, see pii.py" }
        C7_idempotency: { status: covered, mechanism: "optional Idempotency-Key header hashed with (principal, history) into an in-process TTL cache bounded by chat_idempotency_cache_max_entries (PLAN 4.6.3/4.6.4), replays the cached Answer" }
        C8_concurrency: { status: opted_out, justification: "each request creates its own query_trace row; no shared-resource read-modify-write" }
        C9_audit:       { status: covered, mechanism: "structured chat_request/chat_request_replayed log lines (conversation id, trace id, refused, refusal reason, citation count, latency) — never the raw message or answer text; PLAN 9.6 (ADR-0008 decision 6) adds a disclosed exception: a human_handoff log line on every refused=True answer does carry raw_query verbatim, for the stub hand-off queue — mirrors the pre-existing query_trace.raw_query DB column keyed by the same trace_id" }
        C10_abuse:      { status: covered, mechanism: "rate limit + history/message-length caps + AnthropicMessagesClient abuse cap (answer_max_input_chars) + breaker; PLAN 7.3/7.4 (ADR-0009): generate_image_analysis is a second, unconditional LLM call whenever a turn has images — chat_max_images_per_turn/chat_max_image_bytes are this call's own abuse control, since answer_max_input_chars only measures text length" }
    - id: PATCH /chat/{trace_id}/feedback
      tier: STATE-MUTATING
      controls:
        C1_auth:        { status: covered, mechanism: "same shared-secret check as POST /chat" }
        C2_rate_limit:  { status: covered, mechanism: "same limiter/key as POST /chat" }
        C3_input:       { status: covered, mechanism: "feedback constrained to Literal[-1, 1]" }
        C4_timeout:     { status: covered, mechanism: "one bound UPDATE statement, no fan-out" }
        C7_idempotency: { status: covered, mechanism: "UPDATE is naturally idempotent — replaying the same value produces the same row state" }
        C8_concurrency: { status: opted_out, justification: "single UPDATE by primary key; last-write-wins is correct for a thumbs up/down toggle" }
        C9_audit:       { status: covered, mechanism: "structured chat_feedback log line (trace id, value)" }
        C10_abuse:      { status: covered, mechanism: "same rate limiter as POST /chat" }
```

Known, documented limitation (not a bug): there is no end-user login system yet, so `principal` is
caller-self-reported, trusted only as far as C1 trusts the calling web proxy. Per ADR-0004's
default-deny model, an absent/unverified principal can only ever see *unrestricted* pages — never a
blanket-access bypass. Real per-user identity is a later phase; the endpoint is already safe in its
absence.

**PLAN 5.3 red-team finding, fixed.** The claim above was not quite true before 5.3: an all-digit
`principal` is read by `PrincipalPermissionPolicy.allowed` as **space-level trust**, granting every
page in that space regardless of `page_restriction` — a real feature, needed by the eval harness's
numeric space-scoping, but never meant to be reachable from an untrusted HTTP `principal`. Closed at
the boundary with a `ChatRequestBody` validator rejecting all-digit `principal` values (422), not by
changing the shared domain policy. See `server/router.py`'s docstring and PLAN.md §0's 5.3 entry.
