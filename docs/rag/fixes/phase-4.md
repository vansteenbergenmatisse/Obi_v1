## Security

Full `securing-http-and-llm-endpoints` 10-control pass on `POST /chat` (STATE-MUTATING + LLM-CALL) and `PATCH /chat/{trace_id}/feedback` (STATE-MUTATING), read directly from `apps/automation/app/features/rag_agent/server/router.py`, not from its own `security_baseline` docstring.

- **[HIGH] C7_idempotency — replay cache is not bound to the request it was created for** — `app/features/rag_agent/server/router.py:172-177,240-248`. `_idempotency_cache` is a `TTLCache[str, Answer]` keyed **only** on the caller-supplied `Idempotency-Key` header string. `_stream_answer` does `cached = cache.get(idempotency_key)` and, on a hit, returns that cached `Answer` **without checking that the replaying request's `history` or `principal` match the original call that produced it**. Idempotency-Key is entirely caller-controlled and unauthenticated (any string, no per-session binding). If two different callers — or the same caller switching `principal` mid-conversation, e.g. a shared web proxy multiplexing several end users behind one backend credential — ever reuse the same key value, the second caller silently receives the first caller's answer, **including its citations, drawn from whatever pages the first caller's principal/scope was permitted to see**. This is a real cross-principal information-leak vector, structurally different from (and weaker than) the Phase 5 `CachingAnswerService` exact-match cache, which is explicitly keyed on `(full history, principal)` and has a dedicated test (`test_answer_cache_does_not_cross_principal_boundary`, `test_chat_endpoint.py:274`) proving it can't cross a principal boundary. The 4.4 idempotency cache has **no equivalent test or guard** — `test_idempotency_key_replays_cached_answer_without_rerunning` (`test_chat_endpoint.py:238`) only exercises the same key + same body twice, never a same-key/different-body-or-principal case. Suggested direction: bind the cache key to a hash of `(idempotency_key, principal, history)`, or reject/recompute on a body mismatch per the standard idempotency-key contract (RFC-style 409/422 on payload mismatch) instead of trusting the header alone.
- **[MEDIUM-HIGH] C2_rate_limit — the limiter key is the same unauthenticated field C1 does not trust** — `app/features/rag_agent/server/router.py:196-201,301,327`. `_rate_limit_key` prefers `f"principal:{principal}"` whenever `body.principal` is present, falling back to client IP only when it's absent. `principal` is caller-self-reported and explicitly documented elsewhere in this same module (line 51-55) as untrusted ("trusted only as far as C1 trusts the calling web proxy"). Because the rate limiter treats it as a trusted partition key, any caller can defeat `chat_rate_limit_per_minute` entirely by sending a distinct `principal` string (e.g. a UUID) on every request — each gets its own fresh sliding window. This undermines both the literal C2 requirement and the "rate limit" half of the C10 abuse-cap story the module's own docstring credits (line 36-37: "C10_abuse: covered - rate limit + ... "). The `AnthropicMessagesClient` breaker (C4) still trips on consecutive *failures*, and `answer_max_input_chars` still caps a single call's size, but neither bounds request *volume*, so this is a genuine, exploitable cost-abuse gap on a real LLM endpoint. Suggested direction: key the limiter on client IP (or an authenticated session/connection identifier) as the primary partition, with `principal` only as a secondary, non-bypassable additional bucket — never the sole or preferred key for an untrusted field.
- **[MEDIUM] C2/C10 — attacker-controlled rate-limit keys cause unbounded limiter memory growth** — `app/shared/rate_limiter.py:24,28`. `SlidingWindowRateLimiter._hits` is a plain `dict[str, deque[float]]`; `allow()` prunes each bucket's *own* stale entries but never removes the bucket itself from `_hits`, even once it's empty. Combined with the previous finding (an attacker can put an arbitrary string into the key via `principal`), a caller who rotates `principal` on every request causes one permanent dict entry per request for the life of the process — unbounded memory growth, not just a rate-limit bypass. `TTLCache` (its sibling in `app/shared/ttl_cache.py`) already solves the equivalent problem with an optional `max_entries` bound; `SlidingWindowRateLimiter` has no analogous cap. Worth fixing alongside the C2 key finding above, since fixing only the key source (IP-based) would still leave unbounded growth possible from real distinct IPs at scale, just harder to trigger deliberately.
- **[MEDIUM] C7 — the idempotency `TTLCache` itself is unbounded, unlike its Phase-5 sibling** — `app/features/rag_agent/server/router.py:172-177`. `TTLCache[str, Answer](settings.chat_idempotency_ttl_seconds)` is constructed with **no `max_entries`** argument, so `TTLCache.set()`'s eviction loop (`app/shared/ttl_cache.py:42-45`) never fires — every distinct `Idempotency-Key` value received stays in memory for the full `chat_idempotency_ttl_seconds` (default 300s), each holding a full `Answer` (text + citations). The Phase-5 answer cache passes `chat_answer_cache_max_entries` explicitly for exactly this reason. Combined with the C2 finding (rate limiting itself is bypassable via `principal` rotation), a caller can drive real Anthropic spend *and* accumulate unbounded idempotency-cache memory in the same request loop. Suggested direction: pass a bound (e.g. a new `chat_idempotency_cache_max_entries` setting, mirroring the answer-cache one) when constructing this cache.
- **[LOW] C9_audit — the computed refusal reason never reaches any audit surface** — `app/features/rag_agent/application/answer_service.py:69-75,84-94` computes and returns `Answer.refusal_reason` (e.g. `"top relevance 0.083 below refusal threshold 0.100"`), but `router.py`'s `chat_request` log line (`router.py:259-266`) logs only the boolean `answer.refused`, never `answer.refusal_reason`; the SSE `done` event (`router.py:280-288`) and the TS `ChatDoneEvent` contract (`packages/contracts/src/index.ts`) likewise omit it; and `_persist`'s `update_query_trace_answer` call (`answer_service.py:129-145`) never writes it to `query_trace` either. The one piece of data that would tell an operator *why* a given trace refused is computed, asserted in unit tests (`test_answer_service.py:166,201,228,299`), and then dropped on the floor before it reaches any log, response, or DB row. Not a control failure (C9's minimum bar — actor/action/target/timestamp/outcome — is still met by the boolean), but a real observability gap worth closing cheaply. See also "Dead code" below.
- **[LOW] C9 — generic exception message logged verbatim on generation failure** — `router.py:253-256`: `log.error("chat_answer_failed", conversation_id=..., error=str(exc))`. Traced this end to end: `AnthropicAnswerGenerator.generate` lets `AnthropicError` propagate (by design, per its own docstring), and `AnthropicError`'s messages (`anthropic_client.py:69-76,123,124`) never include the request body/prompt text — only status codes, char counts, and retry counts — so no PII/prompt leakage today. But `service.answer()` can also raise a bare `ValueError` (`answer_service.py:61-62`, precondition check) or, in principle, any other exception from the retrieval stack, and nothing in `_stream_answer` narrows the `except Exception` to a known-safe type before logging `str(exc)`. This is currently safe by inspection, not by contract — a future exception type introduced anywhere in the call chain could leak more than intended into a log line with no compile-time or test guard against it. Low severity given the actual code paths today; worth a comment or an allow-listed exception-to-message mapping if this file is touched again.

**Confirmed genuinely correct on the remaining controls** (read the code, not just the docstring):
- **C1** (`router.py:180-193`) — real double `hmac.compare_digest` against both `chat_api_key` and `chat_api_key_previous`, both always evaluated (no short-circuit timing tell), fails closed (503) when unconfigured. Matches the docstring exactly.
- **C3** (`router.py:111-131,203-217`) — `extra="forbid"` on both `ChatRequestBody` and the nested `ChatMessage`/`FeedbackBody`; non-empty history ending on a user turn; per-turn and per-history length caps enforced before any retrieval/LLM work starts.
- **C4** — `AnthropicMessagesClient` (`anthropic_client.py:38-124`) has a real bounded timeout, exponential-backoff retry (`0.3 * 2**attempt`, capped 4s), and a genuine consecutive-failure breaker that resets to zero on any success (line 83) — not a fake always-open/always-closed stub.
- **C5** (`router.py:270-276`) — defensive re-cap (`chat_output_max_answer_chars`) applied on top of the generator's own token cap, then chunked and paced via `asyncio.sleep`.
- **C6** (`llm_client.py:63-95`) — `redact_pii` is applied at both Anthropic call sites, on the fully assembled prompt (including history and evidence, not just the raw user string) immediately before the network call.
- **C8** — both opt-outs (`router.py:31-32,46-47`) are real, reasoned justifications (new row per request; single-PK UPDATE where last-write-wins is the intended semantics), not empty placeholders.

## Test coverage gaps

- **No test exercises `Idempotency-Key` replay with a *different* `history` or `principal` on the second call** — see the HIGH C7 finding. `test_idempotency_key_replays_cached_answer_without_rerunning` (`test_chat_endpoint.py:238-254`) is the only idempotency test and only covers the identical-body case. This is the one test that would have caught the cross-principal leak risk before it shipped.
- **No test exercises `_rate_limit_key`'s principal-vs-IP branch being gamed** — `test_rate_limit_returns_429` (`test_chat_endpoint.py:174-181`) only checks that a single, fixed key gets limited; nothing asserts (or documents as a known gap) that varying `principal` per request resets the limiter, which is exactly the MEDIUM-HIGH finding above.
- **No test on `SlidingWindowRateLimiter`/`TTLCache` for unbounded-key memory behavior** — `app/shared/tests/` (part of this audit's run, 76 passed total) covers correctness (window sliding, TTL expiry, max-entries eviction where a bound is configured) but nothing asserts a *bound exists* for the idempotency cache's construction in `router.py`, so a future regression removing the answer-cache's `max_entries` config wouldn't be caught by any existing assertion.
- Per the task's scope boundary, the 5.3-added `test_numeric_principal_is_rejected_not_treated_as_space_wide_trust` (`test_chat_endpoint.py:157-171`) exists and passes, but its own adequacy is explicitly out of scope for this round (Phase 5 audit's job) — noted only for completeness.
- Web side: 39/39 vitest tests pass across `validation.test.ts`/`chat-client.test.ts`/`route-handlers.test.ts`; per the 4.5 ledger's own "Not done" section (`PLAN.md:393-400`), there are still no component-render tests for `message-list.tsx`/`chat-panel.tsx` (no jsdom/RTL) — an explicit, previously-flagged scope decision, not a new gap found here.

## Deferred / future ideas

- No end-user login/identity system exists anywhere in the repo (`apps/web` or `apps/automation`) — `principal` remains caller-self-reported for both `POST /chat` and the browser UI (which today never even sends one — confirmed in `apps/web/src/features/chat/ui/chat-panel.tsx:66`, `streamChat` is called with only `conversationId`/`history`). Real per-user identity is a later, separate phase, already documented as such in `router.py`'s docstring and `FEATURES.md`.
- NER-grade PII detection is intentionally not built; `rag_agent/domain/pii.py`'s regex set (email/phone/SSN/card) is a documented, deliberately basic first pass.
- No component-render tests for the web chat UI (jsdom/RTL never added) — explicit scope decision from 4.5, re-confirmed still true.
- No ESLint config anywhere in `apps/web` — pre-existing, unrelated to this phase, previously flagged.
- Screen-reader and narrow-viewport verification for the chat UI was flagged by the 4.5 design-review agent as not independently re-run; still true, not re-verified in this pass (out of this audit's tooling — no live browser drive was performed here).
- **New idea worth capturing:** the asymmetry between the Phase-5 `CachingAnswerService` (principal-scoped, tested) and the Phase-4.4 idempotency cache (not principal-scoped, untested for mismatch) suggests these two caches should either share one principal-aware keying discipline, or the idempotency cache should be documented as "trusted caller only" with a comment explaining why it's allowed to be weaker — right now the asymmetry looks accidental rather than a reasoned design choice.

## Confirmed correct

- **C1 auth**: real constant-time double-compare (current + previous key), fail-closed on unconfigured secret, no timing tell between "matched current" vs "matched previous" (`router.py:180-193`).
- **C3 input validation**: Pydantic `extra="forbid"` end to end, non-empty/user-terminated history, per-turn and per-history caps, checked before any expensive work (`router.py:111-131,203-217`).
- **C4 timeout/retry/breaker**: `AnthropicMessagesClient` has a genuine timeout, bounded exponential-backoff retry, and a real consecutive-failure breaker that resets on success (`anthropic_client.py:38-124`).
- **C5 output pacing**: real defensive re-cap plus paced, fixed-size SSE chunking (`router.py:270-276`).
- **C6 PII redaction**: applied at both Anthropic call sites on the fully assembled prompt, not just the raw user string (`llm_client.py:63-95`).
- **C8 opt-outs**: both are real, non-empty, sound justifications, not placeholders (`router.py:31-32,46-47`).
- **Citation enforcement cannot be bypassed by construction**: `enforce_citations` (`domain/citations.py:27-43`) operates on the complete generated text sentence-by-sentence; a sentence survives only if it cites a marker in the caller-supplied `valid_markers` set (built from the actual retrieved-hit count, `answer_service.py:80-82`), and any marker outside that set is stripped even from an otherwise-kept sentence (`_drop_invalid_markers`). Zero surviving citations degrades to a refusal (`answer_service.py:84-94`), never an empty/uncited answer.
- **Refusal threshold + CRAG ordering exactly matches ADR-0005 §7/§8**: `decide_refusal` (`domain/refusal.py:23-36`) refuses on `None` or below-threshold top score; `AnswerService.answer` (`application/answer_service.py:60-75`) runs the CRAG retry (`_apply_crag_retry`, line 67) **before** the refusal decision (line 69) — verified directly in the source, not just from the docstring — matching ADR-0005's explicit design note that refusing before ever retrying would defeat the retry's purpose.
- **"Fixed workflow, not an agent loop"**: `AnswerService.answer` is one straight-line function with no loop, no tool-use, no re-planning — every stage (rewrite → retrieve → CRAG → refuse → parent-expand → generate → enforce-citations) runs exactly once per request, matching ADR-0005 §5 and PLAN.md's Phase 4 goal statement verbatim.
- **`page_restriction` write path is a true replace, not an append**: `_replace_restrictions` (`confluence_sync/application/sync_service.py:155-164`) unconditionally deletes all rows for the page, then re-inserts the current, deduplicated principal list only if non-empty (an empty list correctly leaves zero rows = unrestricted); guarded by `restrictions_changed` (line 111) so an unchanged page costs nothing extra on a reconcile tick.
- **`page_restriction` read path is scoped to the candidate set, not the whole corpus**: `fetch_page_scopes` (`retrieval/infrastructure/search_repo.py:168-193`) takes `page_ids: Sequence[int]` and both its queries filter `WHERE page_id = ANY(:page_ids)`; called from `HybridRetriever._search` (`application/retriever.py:140`) with `ranked` — the already-fused candidate list — never the full table.
- **Web proxy never exposes the backend secret or base URL to the browser**: `readAutomationApiConfig` (`platform/automation-api/client.ts:23-32`) reads `process.env.CHAT_API_KEY`/`AUTOMATION_API_BASE_URL` server-side only; no `NEXT_PUBLIC_` variable exists anywhere in the automation-api or chat feature code (grepped); the key is injected as an `Authorization` header only on the outbound server-to-server `fetch` (`client.ts:48-51`).
- **SSE passthrough is a true byte passthrough**: `handlePostChat` (`route-handlers.ts:145-152`) constructs `new Response(backendResponse.body, ...)` directly from the upstream `ReadableStream` — no intermediate buffering, decoding, or re-chunking of the event stream.
- **Backend and web test suites, typecheck, and lint/type baselines all green** at exactly the numbers the ledger claims (see Verification run above) — independently re-run, not trusted from the self-report.
