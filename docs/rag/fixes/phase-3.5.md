## Security

- **[LOW]** 3.5.3 — RLS is currently a no-op in this developer's actual running dev environment, not just "acceptable by design" in the abstract — `apps/automation/app/platform/config/settings.py:30`, `.env.example:59-61`. `database_reader_url` defaults to `""`, and `.env.example`'s `DATABASE_READER_URL=` line is commented out; the real (gitignored) `.env` in this checkout also has no `DATABASE_READER_URL` set. `get_reader_engine()` (`app/platform/db/engine.py:33-48`) therefore falls back to `database_url`, i.e. the superuser `rag` role, which bypasses RLS unconditionally. If `uvicorn app.main:app` were run right now against this same Postgres, `HybridRetriever` (wired via `get_reader_sessionmaker()` in `app/main.py:76`) would read as the bypassing superuser and the `chunk_source_read` policy would never bite — the isolation control that ADR-0004 calls the security boundary is inert outside the test harness. This is a documented, intentional fallback (`settings.py:29` says so explicitly) and the test suite *does* wire a real `rag_reader` role (`confluence_sync/tests/conftest.py:38-90`), so the mechanism itself is proven — but nothing currently forces a real deployment (or this local dev instance) to actually set `DATABASE_READER_URL`. Suggested direction: at minimum, log a startup warning when `database_reader_url` is empty and `env` is not in the offline set, so an operator notices RLS is inert before shipping; a stronger option is to fail closed (refuse to start) outside `local`/`dev`/`test`/`ci`.

## Plan / design deviations (docs vs. code disagree, or an acceptance criterion isn't actually met)

- **[Documented, verified-as-stated]** 3.5.3 — Migration `0002_provider_tags_and_rls.py` keeps the `server_default` on `source_type`/`source_id`/`tags` instead of dropping it as PLAN.md §3.5.3 task 2 originally specified. This is explicitly called out as a deviation both in the migration's own docstring (`0002_provider_tags_and_rls.py:11-15`) and in `PLAN.md:770` ("Source columns keep their `server_default`... keeps the migration-built and create_all-built databases to the same shape"). Confirmed intentional and already tracked — not a new finding, but re-verified as accurately described.
- **[NEW, medium]** 3.5.3 — The "migration-built and create_all-built databases are byte-for-byte the same shape" invariant that `0002`'s docstring and `schema.py`'s module docstring both assert is **not actually true** for the `source_type` CHECK constraint on `chunk` and `page_source`. Root cause: `Base`'s `NAMING_CONVENTION` (`app/platform/db/base.py:13`) is `"ck": "ck_%(table_name)s_%(constraint_name)s"`. The ORM model already gives the constraint a fully-qualified explicit `name="ck_chunk_source_type"` (`models.py:333`; same pattern at `models.py:151` for `page_source`). SQLAlchemy's naming convention machinery re-prefixes that literal string as if it were the bare discriminator, so `Base.metadata.create_all()` (which is exactly what migration `0001_core_schema.py:26` runs) actually creates a constraint named **`ck_chunk_ck_chunk_source_type`** — verified directly via `Base.metadata.tables['chunk'].constraints` with no DB involved. Migration `0002` then runs raw SQL (`0002_provider_tags_and_rls.py:52-55`) that drops-if-exists and re-adds a *differently, correctly* named `ck_chunk_source_type`. Net effect, confirmed live on the dev DB (`\d chunk`, `\d page_source`): **both tables carry two CHECK constraints enforcing the identical predicate** (`ck_chunk_ck_chunk_source_type` + `ck_chunk_source_type`, and the `page_source` equivalents). The DB the test harness builds (`schema.create_all` only, no `0002` DDL — see `confluence_sync/tests/conftest.py:70-74`) has **only** the doubled-name one. So the migration path and the test-harness path do *not* produce the same constraint set, contradicting the explicit claim. Functionally harmless today (same check expression, so no query/write behaves differently), but it is real, permanent schema cruft that `alembic downgrade` never fully unwinds (0002's downgrade only drops the raw-SQL-named copy, correctly leaving the 0001-created one — which is *technically* correct reversibility, but means the 0001-baseline state itself already carries the oddly-doubled name in every environment). The real risk is future drift: if the allowed `source_type` list is ever extended, it must be changed in the ORM model (`models.py:52`) — which only affects fresh `create_all` builds — **and** a new migration must re-run the raw DDL against `ck_chunk_source_type` on already-migrated databases, or the two constraints silently diverge. Suggested direction: wrap the ORM `CheckConstraint` names in `sqlalchemy.schema.conv(...)` (or drop the explicit `name=` and let the convention generate it once) so `create_all` and future migrations agree on one name, then squash the duplicate in a follow-up migration.
- **[Documented, verified-as-stated]** 3.5.6 — `resolve_space_scope` taking every recorded root (active or not), not just active ones, is exactly as PLAN.md §0 (3.5.6 entry, "Deviations from the spec as written," point 2) and the function's own docstring (`scope_resolver.py:71-82`) describe. Read (not just trusted): `if not all_roots: return ScopeResolution(allowed_page_ids=None, ...)` (zero rows ever → `None` → unrestricted) vs. `active_roots = [r for r in all_roots if r.is_active]` then unioning only active roots' coverage, which correctly yields `allowed=set()` (an empty *set*, not `None`) when rows exist but all are inactive — the two cases are genuinely distinguishable in the return type, matching the documented intent. `reconciliation.py:164-170` (`_sweep_space`) treats `allowed_page_ids is None` as unrestricted and an empty set as "scope everything out," which is the correct consumption of that distinction.

## Test coverage gaps

- **3.5.3** — No test asserts what happens when `database_reader_url` is unset in a *non-offline* `env` (the fallback in `engine.py:41` is silent for every environment, not just local/dev/test/ci — nothing in code or tests distinguishes "offline env, fallback is fine" from "prod-like env, fallback is dangerous"). Given the Security finding above, a test (or a startup assertion) that fails loudly when `env` is e.g. `"prod"`/`"staging"` and `database_reader_url` is empty would close this gap cheaply.
- **3.5.3** — The duplicate-CHECK-constraint deviation above has no test coverage in either direction: nothing asserts the migration-built schema and the `create_all`-built schema produce the same constraint set (the very invariant the docstrings claim), so this class of drift would not be caught by CI if it worsened (e.g., if the two constraints' allowed values were ever edited independently).
- **3.5.5** — `evaluate_rerank_lift`'s live, *measured* numbers (precision@5 0.200→0.200, ndcg@10 1.000→0.877) are not reproduced by any test in this run (no `EVAL_WRITE_RERANK_REPORT=1` / live Cohere key available in this sandbox) — this is expected and explicitly documented as a live/manual measurement, not a gap in the mechanism. The mechanism itself (pure function, before==after under `FakeReranker`) is fully covered by `test_rerank_lift.py`'s three unit tests plus the DB-backed `test_rerank_lift_before_vs_after`, all of which passed here with `FakeReranker` on both sides (the CI invariant).
- **3.5.4** — No test directly asserts that `query_trace` inserts *would* be blocked if accidentally run through the reader session (i.e., a negative control proving the writer-engine choice actually matters, not just that it's used). Low priority — the reasoning is sound and RLS is already proven default-deny elsewhere — but a single test forcing a trace write through `get_reader_sessionmaker()` and asserting it raises/returns zero rows would make the "RLS never blocks the insert" claim self-verifying rather than reasoned-about.
