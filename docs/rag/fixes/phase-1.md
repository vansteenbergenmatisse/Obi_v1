## Security

- **[CRITICAL]** Confluence **group-based read restrictions are silently dropped**, and a group-only-restricted page syncs as fully **unrestricted** — `app/platform/clients/confluence_client.py:163-175` (`HttpConfluenceClient.get_restrictions`) and `app/platform/clients/fixture_confluence_client.py:174-182` (`FixtureConfluenceGateway.get_restrictions`, the exact mirror) both parse **only** `restrictions.user.results[].accountId` and never look at `restrictions.group.results`. The fixture corpus itself proves this isn't hypothetical: `tests/fixtures/confluence/restrictions/page-2002.json` encodes a real Confluence-shaped restriction with one user (`acct-carol`) **and two groups** (`grp-hr`, `grp-finance`), and `test_job_queue... ` — actually `test_worker_sync.py::test_first_index_persists_restrictions` — asserts the persisted ACL for that page is `{"acct-carol"}` only, i.e. the two group restrictions are asserted-away as expected/normal in the test itself. Per `FEATURES.md:27` and `sync_service._replace_restrictions` (`sync_service.py:155-164`), **"presence of a row restricts, absence means unrestricted."** A real Confluence page restricted *only* by group (no individual user restriction — a very common enterprise pattern, e.g. "restricted to the Finance group") would therefore fetch `[]` from `get_restrictions`, persist **zero** `page_restriction` rows, and the retrieval permission filter (ADR-0005, Phase 4.3) would treat it as **world-readable through the chatbot** despite Confluence itself restricting it. This defeats the page-level ACL layer for a realistic and probably common restriction pattern, not an edge case. **Why it matters:** this is the exact hard-security-boundary the page-level ACL exists to enforce (ADR-0004 §2 "page-level principal ACL... enforces per-page read restrictions within a source"); a silent gap here is a real data-exposure bug, not a missing nice-to-have. **Suggested direction:** expand group principals to member account ids at sync time (one more Confluence API call per group, cacheable) — or, at minimum, until group expansion is built, treat "restrictions present but only as groups" as **restricted-to-nobody-resolvable-here** (fail closed) rather than silently mapping to `[]` (fail open). This is a sync-path (Phase 1 gateway) defect independent of Phase 4's separately-tracked "group-based principals aren't modeled yet" ACL-enforcement gap — flagging here since it originates in `get_restrictions`, squarely in this audit's scope.

- **[MEDIUM]** Outbound Confluence HTTP client has **no circuit breaker**, unlike its sibling outbound clients — `app/platform/clients/confluence_client.py:80-90` (`HttpConfluenceClient._get`, the sole `@retry`-wrapped call site) has timeout (`settings.provider_timeout_seconds`) and bounded retry/backoff, but no consecutive-failure breaker. Compare `app/platform/clients/embeddings_client.py:75-124`, which implements exactly this (`self._breaker_threshold`, trips after N consecutive failures, per the C4 control DESIGN.md says every outbound client should carry — DESIGN.md:232 explicitly says the reranker client "mirrors the embeddings abstraction exactly... timeout, bounded retry+backoff, circuit breaker"). During a sustained Confluence outage, every queued job independently retries via job-level backoff (`queue.py::fail_job`), but nothing short-circuits repeated in-process HTTP attempts across many jobs/pages the way a breaker would. **Suggested direction:** add the same consecutive-failure breaker pattern from `embeddings_client.py` to `HttpConfluenceClient`.

- **[MEDIUM]** Retry predicate excludes 5xx, contradicting the documented behavior — `confluence_client.py:27` `_RETRYABLE = (httpx.TransportError, httpx.TimeoutException)`. `_get` (`confluence_client.py:86-90`) raises `httpx.HTTPStatusError` via `resp.raise_for_status()` when `resp.status_code >= 500`, but `HTTPStatusError` is **not** in `_RETRYABLE`, so tenacity's `retry_if_exception_type(_RETRYABLE)` never retries a 5xx — it reraises on the first attempt (`reraise=True`). This contradicts `docs/rag/how_this_works.md:321`, which explicitly claims "tenacity retries (3 attempts, exponential backoff, retry on 5xx / transport errors)". Job-level backoff (`queue.py::fail_job`) still eventually recovers a transient 5xx, so this is a resilience/latency gap and a doc/code mismatch, not data loss. **Verdict: the code is the bug, not the doc** — the documented intent (and the sibling `embeddings_client.py:124`'s `resp.status_code in _RETRYABLE_STATUS or resp.status_code >= 500` pattern) is clearly to retry 5xx. See also "Plan / design deviations" below.

- **[LOW]** Fail-open 4xx coalescing on auxiliary metadata endpoints — `confluence_client.py:140-175` (`get_labels`, `get_attachments`, `get_restrictions`) each do `if resp.status_code >= 400: return []`. Because `_get` already raises before returning for `>=500` (see above), this branch only ever sees 4xx, but a 403 (e.g. the sync service account itself losing visibility into a page's restriction list — token/scope regression, or a page whose restriction now excludes even the service account) is indistinguishable here from a genuine "no restrictions" 200, and `_replace_restrictions` treats the fetched list as the current, complete truth (full delete+insert). A 403 specifically on `/restrictions` should arguably fail the sync (keep the prior persisted ACL) rather than be silently read as "unrestricted." Lower severity than the CRITICAL finding above because it requires an access/auth regression on the service account itself to trigger, rather than being a day-one gap in ordinary group-restricted content.

- **[LOW]** `event_repo.record_event`'s `on_conflict_do_nothing(index_elements=["payload_hash"])` (`app/features/confluence_sync/infrastructure/event_repo.py:30-49`) targets only the `uq_event_ledger_payload_hash` unique constraint, not the separate partial-unique `ux_event_ledger_delivery_id` index (`app/platform/db/models.py:365-372`, `WHERE delivery_id IS NOT NULL`). If the same `delivery_id` is redelivered with a different computed `payload_hash` — plausible because `EventEnvelope.event_timestamp` (`schemas/events.py:41`) defaults to `datetime.now(UTC)` whenever the raw webhook body lacks a `timestamp`/`event_timestamp` key (`parse_webhook_payload`, `schemas/events.py:108-110`), so two deliveries of the same logical event without that key hash differently every time — the INSERT collides on the `delivery_id` index instead, which the payload_hash-only `ON CONFLICT` clause does **not** catch: SQLAlchemy/psycopg raises an uncaught `IntegrityError`, which propagates out of the webhook handler as an unhandled 500 instead of the intended graceful `duplicate=True` response. **Untested**: every fixture in `test_webhook.py`/`test_event_dedup.py` either omits `delivery_id` entirely or reuses byte-identical envelopes, so this collision path has never been exercised. Real-world risk depends on whether Confluence's actual webhook payloads reliably include a timestamp field and stable `delivery_id`s — not verifiable offline (the live token is dead per `how_this_works.md:327`) — but the code path itself is a genuine, demonstrable gap in the "idempotency is layered three deep" claim (`how_this_works.md:229-231`) for this specific case.

- **[INFO]** `log = get_logger("confluence_client")` (`confluence_client.py:25`) is assigned but never called anywhere in the file — zero audit/observability logging on the outbound Confluence surface (no log line on retries, 4xx/5xx responses, or any request). Not itself a vulnerability, but a minor C9 (audit logging) gap for this outbound HTTP surface relative to how thoroughly the webhook side logs (`webhook.py:115-126`).

- No secret logging found anywhere in `webhook.py`, `confluence_client.py`, or `event_repo.py` — the webhook's structured log line (`webhook.py:115-126`) logs actor/event_type/page_id/delivery_id/outcome flags only, never the raw payload or the HMAC secret. Confirmed clean.

## Deferred / future ideas

- The general "group-based principals aren't modeled" ACL-enforcement gap is explicitly tracked as Phase 4 scope per PLAN.md's Phase 4.3 notes. The concrete sync-side manifestation of that same gap — `get_restrictions` dropping group restrictions entirely, causing group-only-restricted pages to sync as unrestricted — is reported above under Security/CRITICAL since it originates in this audit's scope (the Confluence gateway), independent of whatever principal-list *format* Phase 4 eventually settles on.
- Rate limiter (`shared/rate_limiter.py`) and the (currently absent) Confluence circuit breaker are both single-process/in-memory by design; multi-instance deployment would need a shared store (Redis) — already explicitly called out as deferred in both `webhook.py`'s docstring (C10) and `shared/rate_limiter.py`'s own docstring, consistent with the CLAUDE.md proportionality gate (no Redis without a confirmed multi-instance requirement).
- `JobStatus.cancelled` is modeled but has no cancel path anywhere (API, admin action, or otherwise) — worth deciding whether to build one or drop the unused enum value.
- Nothing found in the sync path that's an exact equivalent of "principal ACL is fixture-only" (that gap was closed at Phase 4.3, and its data source — `page_restriction`, written by this feature — is real and DB-backed); the closest analog is the group-principal gap above.

## Confirmed correct

- **Worker three-transaction crash-safety pattern** (`worker.py:85-129`) holds exactly as documented and as claimed: transaction 1 (claim, `worker.py:94-100`) commits the lease/attempts increment independently via its own `session_scope()`; transaction 2 (`worker.py:111-120`) runs the handler and `complete_job` inside one `session_scope()`, so the mutation and the `succeeded` transition can only commit together; transaction 3 (`worker.py:121-128`) is a fully separate `session_scope()` that records the failure if transaction 2 raised, independent of transaction 2's rollback. Verified by direct inspection of the code (not just trusting the docstring) and cross-checked against `test_job_queue.py::test_reap_reclaims_expired_lease` and `::test_fail_backs_off_then_dead_letters`.
- `claim_job`'s `FOR UPDATE SKIP LOCKED` (`queue.py:66-87`) and `enqueue_job`'s `ON CONFLICT DO NOTHING` on `idempotency_key` (`queue.py:25-53`, unique constraint confirmed at `models.py:418` `uq_job_idempotency_key`) both verified in code and exercised by `test_job_queue.py::test_claim_uses_skip_locked`.
- The three-deep idempotency chain (event dedup → job idempotency_key → version guard) is verified for the ordinary exact-duplicate case end to end: `test_event_dedup.py::test_duplicate_delivery_is_idempotent`, `test_webhook.py::test_duplicate_delivery_is_deduped`, `test_worker_sync.py::test_version_guard_drops_stale_update`. (The one gap in this chain — mismatched hash with a repeated `delivery_id` — is reported above.)
- Webhook security controls all present and tested: fail-closed on unset HMAC secret (503, `test_webhook.py::test_unset_secret_fails_closed`), constant-time HMAC compare (`webhook.py:67-77`), missing/bad signature → 401, body-size cap → 413, rate limit → 429, self-generated-event suppression with no job enqueued.
- Reconciliation's base sweep (lightweight drift detection, complete full re-verification, orphan deactivation) matches `how_this_works.md` §4.7 exactly; the 3.5.6 scope-union addition (brand-new-space discovery via `source_scope`, purge-on-root-removal) preserves the pre-3.5.6 "zero rows → unrestricted" behavior byte-for-byte when no `source_scope` row exists, so it doesn't regress base reconciliation (confirmed by inspection; deep-diving the 3.5.6-specific tests themselves is that agent's job, not re-litigated here).
- `CONFLUENCE_SPACES`/`confluence_scope_list` dead code fully removed, no lingering references anywhere.
- ruff clean across the entire audited scope. All 5 in-scope pyright errors (3 in `sync_service.py:121-123`, 1 in `confluence_client.py:137`, 1 in `queue.py:131`) trace via `git blame` to the initial baseline commit `e10ee9d` — none are regressions; the repo-wide pyright total (34 errors) matches the stated current baseline exactly.
