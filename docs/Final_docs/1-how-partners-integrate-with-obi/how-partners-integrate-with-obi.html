Obi · partner integration

How partners integrate with Obi

A partner page loads Obi's script and hands Obi a short-lived signed token that names the customer and the connection: a source system and a target system. The source decides whether Obi appears.

The source decidesMews, Toast or Opera Cloud as source → Obi shows. Anything else → Obi hides.
The target is never checkedAny target is accepted. One we have no pages for falls back to the source's pages.
No token = no connectionWithout a token the widget still works, but answers are not narrowed to the customer's connection.

How a question travels

The partner's server signs the token; Obi's backend verifies it. Nothing in the request body decides access.

The token's life

The token is fetched fresh, held in memory only, and renewed 60 seconds before it expires.

What Obi does with the token

One question decides visibility: is the source system one we support?

Recorded in ADR-source-system-decides-widget-eligibility. Hiding uses the visibility probe from ADR-widget-hides-via-visibility-probe.

Part A · for the partner

What the partner builds

Five steps, in order. Each names what we need back.

  1. Tell us where the widget loads. Every https origin, e.g. https://base.development.omniboost.io. Every page on the host is covered.
    We need: the exact origins.
  2. Publish a signing key (JWKS). RS256 or ES256, each key with a kid. Rotate by publishing the new kid before signing with it. 
    { "keys": [ { "kid": "base-2026-10", "kty": "RSA", "alg": "RS256",
              "use": "sig", "n": "<modulus>", "e": "AQAB" } ] }
    We need: the JWKS URL and the exact iss string.
  3. Build the token endpoint. Same origin as the page, uses the user's session, returns {"token": "<jwt>"}. 
    { "iss": "https://base.development.omniboost.io", "aud": "obi", "sub": "5",
  "iat": 1792072431, "exp": 1792072731,
  "source_system": "Toast", "target_system": "NetSuite", "business_id": 2108 }
    iss letter for letter · aud is "obi" · exp − iat ≤ 60 min · names in any case or spacing · business_id string or number · 60 s clock skew tolerated.
    We need: the deployed tokenUrl (not .test) and one fresh token.
  4. Add the widget. 
    <script src="https://obi-web-production.up.railway.app/obi.js"></script>
<script>Obi.init({ tokenUrl: "/obi/token" });</script>
    Obi.init again to switch customer (fresh chat) · Obi.clear() on logout · Obi.destroy() removes it.
  5. Test it. Load a page on a listed origin, ask a question, send us a fresh token, then test again after we activate your entry.

Who does what

Partner

  • List the https embed origins
  • Publish the JWKS (RS256/ES256, kid)
  • Give us the exact iss
  • Deploy tokenUrl returning {"token": …}
  • Put the real source_system, target_system, business_id in each token
  • Add the snippet; re-init on customer switch; clear() on logout
  • Send one fresh token from the deployed environment

Obi team

  • Add the origins to an active entry's domains
  • Fill issuer, jwks_url, algs in platforms.json
  • Check the JWKS returns keys; verify the fresh token
  • Validate under production settings
  • Set active: true; remove the hosts from obi-test
  • Redeploy backend and frontend; check /health and the /embed header
  • Run the test with the partner
Part B · for us

Our side

What we register per partner

Field in platforms.jsonWhat it does
issuerLooks up the partner from the token's iss. Must match exactly.
jwks_urlWhere Obi fetches the public keys, by kid.
domainsEmbed hosts, no scheme. Only active entries count: they feed the /embed frame-ancestors header and the frame's message allow-list.
lifetime_minutesLongest accepted exp − iat (1–1440; we use 60).
algsRS256 and/or ES256.
activeOnly active entries are served; a token from an inactive entry is refused (401).
allowed_integrationsThe source systems this partner may assert; any other source is refused (401).

Supported sources and routing

enabled_sources in product_catalog.json lists the sources that make Obi appear: mews, toast, opera-cloud. For Toast → Mews Obi searches only pages labelled obi-general, toast-general, mews-general, toast-to-pms; an unknown target keeps the first two. See product-catalog.md and the labels in use.

Deploying

A git push does not deploy. Backend: railway up --service obi-backend --detach (runbook). Frontend: scripts/deploy-frontend.sh (runbook). obi.js bakes in the Obi origin and the source names, so catalog changes need a frontend redeploy; platforms.json changes need both.
